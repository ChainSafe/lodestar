# Dirk: Feature Analysis Relative to Lodestar (High-Availability Focus)

Dirk is Attestant's distributed remote signer, written in Go. It holds validator keys in encrypted wallet stores, exposes a gRPC signing API over mandatory mutual TLS, enforces per-client permissions and slashing rules, and can generate threshold keys across a cluster of Dirk instances so that no single instance holds a whole key. Vouch is its only native client; Vero can reach it through a third-party translator (see [vero-feature-analysis.md](./vero-feature-analysis.md)). This document records what Dirk provides at the signer layer that the Lodestar stack does not, with emphasis on redundancy and high availability (HA).

Lodestar has no signer product. Its signer layer is the validator client's local keystores plus a client for the Ethereum Remote Signing API, typically pointed at Web3Signer. Comparisons below are therefore against that stack, citing `L6`, `L7` and `L8` from the [Lodestar HA baseline](./lodestar-ha-baseline.md).

Snapshot: Dirk `1.3.0-rc.1` at commit `9429ac80`, cloned 2026-09-24 to `packages/high-availability/.research/dirk`. Client-side composition behaviour is cited from `wealdtech/go-eth2-wallet-dirk v1.6.0`. Paths are relative to `.research/` unless prefixed with the library name.

## Executive summary

- **Threshold keys are the redundancy mechanism.** A validator key is generated by distributed key generation (DKG) across n Dirk instances with signing threshold m, where m must exceed n/2. Each instance signs with its share; the client recovers the composite signature from any m partials. Up to n-m instances can be down and signing continues. No key material ever exists whole (`L7`).
- **Slashing protection lives at the signer and is fail-closed.** Each instance keeps the highest source epoch, target epoch and proposal slot per pubkey in BadgerDB and denies any attestation whose target is not strictly greater than the last, and any proposal whose slot is not strictly greater than the last. Identical re-signing is denied too. This is stricter than the EIP-3076 minimum and is what makes several validator clients on the same keys safe (`L8`).
- **Safety composes with the threshold.** Protection is per instance with no replication, but a conflicting composite signature requires m approvals, so the cluster stays safe as long as fewer than m instances missed an earlier signing.
- **Strong client authentication.** Every client presents a certificate; permissions are keyed by certificate common name, wallet and account regex, and operation. Voluntary exits require an admin IP allow list. Generic signing refuses attester and proposer domains so the rules cannot be bypassed (`L6`).
- **Operational gaps.** No resharing or participant replacement for existing keys, no hot reload of permissions or peers, no runtime interchange import or export, no replication of protection state, and the signing threshold is client-enforced rather than server-enforced.

## Architecture and API surface

Dirk is a single daemon (`dirk/main.go:76-160`). Startup loads stores, an unlocker, a permission checker, a fetcher that decrypts every wallet and account into memory, a per-key locker, the rules engine with its BadgerDB, then the lister, signer, peers, DKG process, account and wallet managers, and finally the gRPC server. `dirk_ready` flips to 1 only after all services start (`dirk/main.go:280-322`, `:585-755`). Dirk never contacts a beacon node; chain-specific data such as domains arrives inside signing requests. Externally added keys require a restart; DKG-created accounts are added live.

| gRPC service     | RPCs                                                                                         | Purpose                                                                                                                                                                                                                    |
| ---------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Lister`         | `ListAccounts(paths[])`                                                                      | Returns accounts and distributed accounts (name, pubkey, composite pubkey, signing threshold, participants), filtered by the `Access account` permission (`dirk/services/api/grpc/handlers/lister/listaccounts.go:60-95`). |
| `Signer`         | `Sign`, `Multisign`, `SignBeaconAttestation`, `SignBeaconAttestations`, `SignBeaconProposal` | Account addressed by name or pubkey; each returns SUCCEEDED, DENIED, FAILED or UNKNOWN.                                                                                                                                    |
| `AccountManager` | `Lock`, `Unlock`, `Generate(account, passphrase, signing_threshold, participants)`           | `Generate` drives DKG, or plain generation when participants is 1.                                                                                                                                                         |
| `WalletManager`  | `Lock`, `Unlock`                                                                             | Wallet-level lock state.                                                                                                                                                                                                   |
| DKG receiver     | `Prepare`, `Execute`, `Commit`, `Abort`, `Contribute`                                        | Peer to peer; caller must be a configured peer.                                                                                                                                                                            |

Interceptors tag every call with a request id, the source IP and the client certificate's common name (`dirk/services/api/grpc/interceptors/`).

## 1. Cluster model

### 1.1 Identity, peers and certificates

Each instance has a numeric `server.id`, used directly as its BLS participant id, and a `server.name` that must equal the DNS name in its server certificate (`dirk/main.go:97-99`, `:691-700`, `dirk/util/bls.go`). A static `peers` map of id to `name:port` must include the instance itself and is identical across the cluster; it is used only for DKG participant selection and peer authentication (`dirk/services/peers/static/service.go:36-72`). Dirk-to-Dirk calls present the instance's server certificate as client certificate over TLS 1.3, and the receiver maps the caller's common name to a peer id, rejecting unknown senders (`dirk/services/sender/grpc/service.go`, `dirk/services/api/grpc/handlers/receiver/helpers.go:22-34`). All instances must therefore share a certificate authority or trust each other's.

### 1.2 Stores

Each instance has its own wallet stores (filesystem, S3 or scratch, optionally passphrase-encrypted) and its own BadgerDB path. The distributed wallet must exist on every participant before DKG (`dirk/core/stores.go:47-187`, `dirk/docs/distributed_key_generation.md`). Docs recommend separate servers per instance for both security and availability.

### 1.3 Comparison with the Lodestar stack

| Capability                                 | Dirk                                  | Lodestar VC + Web3Signer      | Gap    |
| ------------------------------------------ | ------------------------------------- | ----------------------------- | ------ |
| Signer clustering as a first-class concept | Yes, peers, ids, shared CA            | No, one URL per key in the VC | L6, L7 |
| Key material split across instances        | Yes, DKG threshold shares             | No                            | L7     |
| Signer authenticates the client            | mTLS with per-common-name permissions | VC sends no credentials       | L6     |
| Signer to signer channel                   | Yes, DKG only                         | n/a                           |        |

## 2. Threshold keys

### 2.1 Configuration and enforcement

The threshold is set per key at generation time by the client (for example `ethdo account create --signing-threshold=2 --participants=3`), not in configuration files. Dirk enforces participants at least 1, threshold at most participants, and threshold strictly greater than participants divided by two, so 1-of-3 is refused and a majority is always required (`dirk/services/process/standard/generate.go:43-54`). One participant produces a standard key.

At signing time Dirk does **not** enforce the threshold. Each instance independently validates, checks permissions, runs its rules and returns a partial signature over its share. The threshold is realised by the client needing m valid partials to recover a composite (`dirk/services/signer/standard/`, `go-eth2-wallet-dirk/grpc.go:1187-1233`). The stored threshold is advisory metadata handed to clients through `ListAccounts`.

### 2.2 The DKG protocol

`Suitable(n)` picks the first n peers from the static map (`dirk/services/peers/static/service.go:105-130`). The initiator sends `Prepare` to every participant with the account, passphrase, threshold and participant list. Each participant generates a degree m-1 polynomial, per-participant secret shares and a verification vector. In `Execute`, each participant pushes shares to peers with higher ids via `Contribute`, verifying received shares against the peer's verification vector. In `Commit`, each participant checks it holds shares and vectors from all n, sums shares into its private key share, sums vectors into the composite verification vector, stores the account encrypted with the DKG passphrase or `process.generation-passphrase`, and signs initiator-supplied confirmation data. The initiator checks that all participants report the same composite pubkey and that every contiguous m-subset of confirmation signatures recovers to a valid composite signature (`dirk/services/process/standard/service.go:79-336`, `crypto.go:23-117`, `generate.go:128-269`). Generations older than `process.generation-timeout` (70 s) are dropped.

An unreachable peer fails `Execute` at the first failed contribution and `Commit` if fewer than n contributions arrived; generation aborts with no automatic retry.

### 2.3 Tolerance and limits

- **Signing tolerance.** Any n-m instances may be down, slow or denying; the docs demonstrate shutting down one of three instances and signing still completing (`dirk/docs/distributed_key_generation.md:289`).
- **No resharing.** There is no supported path to rotate shares, add or remove a participant for an existing key, or regenerate a lost share. A helper for aggregating without altering an existing key exists only as commented-out code (`dirk/services/process/standard/crypto.go:66-104`). Changing `peers` requires a restart and affects only future generations.
- **Standard keys have no failover.** Copying wallet files to several instances yields duplicate pubkeys; the Vouch library keeps the first and pins signing to the endpoint that listed it (`go-eth2-wallet-dirk/grpc.go:216-240`, `:785-789`).
- **Client must reach every participant.** The client library opens a connection to every participant even though only m answers are needed; a totally unreachable address fails the request, mitigated by lazy gRPC connects.

## 3. Slashing protection

### 3.1 Store

BadgerDB at `storage-path` with synchronous writes, tables in RAM, and optional periodic value-log garbage collection every 24 hours plus a random offset so co-started instances do not collect together (`dirk/rules/standard/storage.go:37-95`). Per pubkey it stores only the latest values: `(SourceEpoch, TargetEpoch)` and `Slot` (`dirk/rules/standard/signbeaconattestation.go:28-67`, `signbeaconproposal.go:29-64`). There is no full history and no signing roots.

### 3.2 Rules

- **Attestation.** Domain prefix must be the beacon attester domain; target must exceed source unless both are zero; **target must be strictly greater than the previously signed target**; source must be at least the previous source (`dirk/rules/standard/signbeaconattestations.go:151-178`). The consequence is at most one attestation per target epoch per key, even for identical data, plus surround protection in the monotonic-source, monotonic-target form.
- **Proposal.** Domain must be the beacon proposer domain; **slot must be strictly greater than the previously signed slot**, so re-signing the same block is denied (`dirk/rules/standard/signbeaconproposal.go:79-95`).
- **Generic sign.** Refuses attester and proposer domains, forcing use of the protected RPCs; voluntary exits require the source IP to be in `server.rules.admin-ips` (`dirk/rules/standard/sign.go:27-67`). No history is kept for RANDAO, selection proofs, sync committee messages or registrations.
- Rules are compiled Go; there is no scriptable rules engine. Other hooks (list, create, lock, unlock) are unconditional approvals.

### 3.3 Concurrency

The ruler takes a global pre-lock then a per-pubkey mutex for every key in a request, so two concurrent requests for one key are serialised and the second sees the first's state. A batch containing the same pubkey twice is rejected (`dirk/services/ruler/golang/runner.go:55-90`, `dirk/services/locker/syncmap/service.go:55-95`). Attestation batches use a fast path with a single BadgerDB batch write.

### 3.4 Scope: per instance, not shared

Protection state is never replicated, gossiped or agreed between instances; the peer channel carries only DKG RPCs. Cluster-level safety is an emergent property: a conflicting composite signature needs m approvals, and an instance that was down for an earlier signing has stale state and might approve a conflicting request later. The cluster therefore stays safe as long as fewer than m instances missed the earlier signing. This is derived from the rules and the threshold code; the docs do not state it.

### 3.5 Interchange

Offline only, with Dirk stopped. `--export-slashing-protection` writes EIP-3076 v5 with one block and one attestation record per pubkey (the latest values). `--import-slashing-protection` requires format 5, checks the genesis validators root against the file (Dirk does not know the chain otherwise), takes the maximum source, target and slot per key, and overwrites a key only if all fields are at least the existing values (`dirk/slashingprotection.go:61-264`). No runtime import or export, no full history.

### 3.6 Behaviour with several validator clients

Two clients requesting the same duty from the same Dirk: the second request in the same target epoch or slot is DENIED regardless of data equality, so one instance can never emit two attestations per key per epoch or two proposals per slot. Vouch treats DENIED as a failure and, under its static-delay mode, steps back. The rising `dirk_signer_process_requests_total{result="denied"}` counter is the observable signature of competing clients. This denial-driven yielding is the de facto coordination mechanism between validator clients sharing a Dirk cluster, and it is what the Vero sidecar's README refers to when it says Vero and Vouch can share a cluster.

### 3.7 Comparison

| Capability                                  | Dirk                           | Lodestar VC + Web3Signer                                    | Gap |
| ------------------------------------------- | ------------------------------ | ----------------------------------------------------------- | --- |
| Protection enforced where the key is        | Yes, per instance, fail closed | Web3Signer has its own database; the VC also checks locally |     |
| Denies identical re-signing                 | Yes                            | No, identical roots are idempotent in Lodestar              |     |
| Protection across several validator clients | Yes, by denial plus threshold  | Only if all clients share one Web3Signer database           | L8  |
| Replicated protection state                 | No                             | No                                                          | L8  |
| EIP-3076                                    | Latest values only, offline    | Full history, CLI and keymanager API                        |     |
| Voluntary exit gating                       | Admin IP allow list            | Keymanager API bearer token                                 |     |

## 4. Permissions and authentication

Permissions are `permissions.<clientCN>.<wallet[/account-regex]>: [ops]` with operations `All`, `None`, `Sign`, `Sign beacon attestation`, `Sign beacon proposal`, `Access account`, `Create account`, lock and unlock operations, and explicit denial with a tilde prefix. Evaluation walks the client's paths in order, matches wallet and account regex, then scans operations in order; no match denies (`dirk/services/checker/static/service.go:64-118`). Client identity is the common name of the verified certificate, chained to `certificates.ca-cert`. `dirk --show-permissions` prints the table and `--show-certificates` prints issuer, expiry and subject. Lodestar's remote signer client sends no credentials at all, and Web3Signer's authorisation model is out of scope here; the point for HA is that Dirk can grant several validator client identities access to the same wallet with fine-grained operations.

## 5. Unlocking

`unlocker.wallet-passphrases` and `unlocker.account-passphrases` are lists of majordomo URLs resolved at startup. Signing auto-unlocks: the pre-check fetches the account, checks permission, and if the account is locked tries the configured passphrases; failure to unlock is a denial (`dirk/services/signer/standard/helpers.go:22-131`). Explicit lock and unlock RPCs exist for accounts and wallets. DKG shares are encrypted with the client-supplied passphrase or `process.generation-passphrase`, and generation is refused without one.

## 6. Observability

- Metrics: `dirk_ready`, `dirk_start_time_secs`, `dirk_release`, `dirk_checker_permissions{client}`, `dirk_signer_process_requests_total{request=proposal|attestation|generic,result=succeeded|denied|failed}`, `dirk_signer_process_duration_seconds{request}`, account and wallet manager request counters, lister counters, unlocker results (`dirk/metrics.go:14-90`).
- The denied counter per instance is the primary HA signal: it reveals competing clients, or clock and data divergence between clients.
- OpenTelemetry tracing over gRPC with optional mTLS; spans on API handlers, signer, ruler and rules storage.
- Structured JSON logging with per-module levels; trace level logs full signing data.
- No health endpoint beyond `dirk_ready` on the metrics listener.

## 7. Deployment and operations

- **Configuration** by viper file or `DIRK_*` environment variables: `server.{id,name,listen-address,rules.admin-ips,rules.periodic-pruning}`, `certificates.*`, `storage-path`, `stores[]`, `metrics.listen-address`, `tracing.*`, `peers`, `unlocker.*`, `process.{generation-passphrase,generation-timeout}`, `permissions.*` (`dirk/docs/configuration.md`).
- **No hot reload.** Permissions, peers, stores and passphrases are read once. Adding keys externally or granting a new client certificate requires a restart.
- **Cluster deployment** is one instance per host with its own id, certificate, stores and storage path, an identical peers map, a shared CA, and permissions granting the validator client's common name on the distributed wallet on every instance. The docs walk through a three-instance, 2-of-3 setup.
- **Rolling upgrades** are safe by construction with a threshold, though no procedure is documented.
- **Documented gaps.** No procedure for replacing a permanently lost participant, no backup guidance for protection state beyond interchange export, no replication.
- **Secrets** via majordomo (file, direct, Google Secret Manager, AWS Secrets Manager); S3 store back end with custom endpoints.

## 8. What a Lodestar HA signer layer would need to match

Dirk's value for HA comes from four properties that the Lodestar stack lacks today:

1. **Key sharding with a majority threshold**, so the loss of a minority of signer instances does not stop signing and no instance can sign alone (`L7`).
2. **Fail-closed, strictly monotonic slashing rules at the signer**, which turn the signer into the arbiter between competing validator clients (`L8`).
3. **Client identity and per-operation permissions**, so several validator client instances can be authorised to the same keys with an audit trail (`L6`).
4. **Client-side composition with a bounded round timeout**, so a slow or partitioned instance degrades rather than blocks (`L6`).

Dirk's weaknesses point at where a new product can do better: replicate or agree protection state between signer instances instead of relying on the threshold to mask stale instances; support resharing and participant replacement; expose runtime interchange import and export with full history; make the threshold server-enforced or at least server-observable; and provide a health endpoint. The post-quantum document in this folder examines the further constraint that the key-sharding property does not carry over to hash-based signatures.
