Lodestar fork choice · TypeScript proto-array vs Zig store

Proto-array keeps the answer in every node. The Zig store keeps only facts and derives the head on request.

Both implement the same spec and pick the same head. They differ in what is stored between calls, and that decides where bugs can hide.

Shape

One layout is a cache of the answer, the other is a table of inputs

Proto-array is the Lighthouse design: every node remembers its weight and the index of its best child and best descendant. A head request follows one pointer. The price is that every vote change must be turned into a delta and pushed up the tree, and every delta must keep those pointers coherent.

The Zig store is the spec Store minus beacon states. Blocks are rows of facts. Weights, viability and best children live in scratch arrays sized three per block, because a Gloas block is three fork choice nodes. A head request rebuilds the arrays from the latest messages and the block table.

Data-oriented

The layout was chosen from what a head computation reads, not from what a block is

Data-oriented design starts from the transformations and their frequencies, then picks the smallest representation that serves them. The fork choice has one hot transformation, head computation, and it reads the same few things every time: every vote, every block's parent and slot, and the balances. Everything else is read once per message.

Why this is the better shape for a fork choice, beyond the benchmark:

  • Hot and cold data are separate. The struct-of-arrays table puts the four columns the head pass reads next to each other and leaves roots, checkpoints and bid hashes in columns the pass never loads. A proto-array node carries all of it in one object, so every visit pulls the cold fields through the cache too.
  • Indices, not pointers or strings. Blocks are rows, nodes are row × 3 + status, validators index their own message. There is no hex conversion, no map lookup inside the hot loop, and prune is a compaction with one index remap.
  • Derived state is a function, not a field. Weights and best children are computed from facts on request. There is no second copy of the vote state, no delta to get wrong, no pointer to repair when a node turns out to be unviable. The stale-head class of bugs cannot exist.
  • Memory is bounded and visible. 16 bytes per validator for votes, 2 for balances, one row per block, three ids per Gloas block. A day of non-finality is 7,200 rows and costs 5 percent on the head pass. No per-object or per-string allocation on any handler.
  • The transformations are the spec. Scatter is get_attestation_score, the reverse pass is filter_node_tree plus the weight sum, the descent is get_head. The data was shaped so the spec functions become array passes, which is why the vectors passed on the first run.
  • The cost model is flat. One pass over validators plus one over blocks, every call, no matter what happened since the last call. Proto-array is cheap when little changed and does extra pointer repair when much changed; the Zig store costs the same on a quiet slot and under a mass reorg or a slashing wave, which is when fork choice must not degrade.

A vote

TS stores a vote as two slots and a delta; Zig stores it as the spec's latest message

The queue is the one place a caller of the Zig store has to do something TS did for it. The Zig store rejects an attestation for the current slot, as the spec does, so the beacon node has to hold it until the next tick.

Head

Incremental deltas versus one full pass over a flat table

Why the full pass is not slower: TS's computeDeltas already visits every validator on every call, so both sides pay the O(validators) scan. The block pass is a few hundred rows and is flat up to a day of non-finality.

Gloas

TS stores a Gloas block as two or three nodes; Zig stores one row and names three node ids

TS

Separate ProtoNode entries

Zig

One row, three ids

Both build the same tree: a block's pending node has its empty and full variants as children, and child blocks hang off empty or full by comparing bid hashes. TS appends a FULL object when the envelope arrives and must re-link; Zig flips one flag and the full id starts existing in the next pass.

Viability

Both apply filter_block_tree, at different moments

The spec rule is the same text in both: voting source epoch equals the justified epoch or is at most two behind, and the finalized checkpoint is an ancestor. TS folds a third rule in, invalid execution status, because optimistic sync lives inside proto-array. Zig has no execution status column yet.

Switching

Run both on the same events before trusting the new one

  1. Done: the fork choice compliance vectors (pnpm download-comptests) pass on every fork, 1473 cases each.
  2. Done: the engine verdict per payload and onPayloadInvalid, the Zig validateLatestHash; node status is derived, never stored.
  3. Done: votes for a slot not yet past are queued in the store, one per validator, and applied on the tick that makes them past.
  4. Ship the Zig store behind a flag in shadow mode: it receives every event, logs each head mismatch, decides nothing.
