# PQ fork findings

Working notes from implementing the consensus-specs `pq` feature (commit `4595f0fc`) in Lodestar with leanVM (`351f7ae4`, bindings v0.19.0, the experimental prover with its CPU tiers) as the prover. The leanXMSS and aggregation measurements were taken at leanVM `1e674918a`. Three kinds of finding: spec deficiencies, implementation difficulties, and measurements.

Measurements are from one machine, an AMD Threadripper 1950X (16 cores, 32 threads, no AVX-512), with `zig build build-exe:bench_pq_signer -Doptimize=ReleaseFast`. They are single runs.

## Spec deficiencies

1. **A leanVM proof does not show which leaf a signature used.** `VerifyAggregates` takes statements of `(pubkeys, leaf_index, message)` and accepts only signatures made at `leaf_index`. The leaf index is the first 4 bytes of a signature, so a raw signature is checked against the leaf its slot or epoch implies. Inside a proof the signature is private input: leanVM proves a set of `(pubkey, message)` claims and its guest constrains the leaf index without publishing it. A key that never reused a leaf is unaffected, since nobody can sign for it at any leaf. A key with one leaf used twice can be impersonated for any attestation inside a proof, by a dishonest aggregator or proposer, where the spec confines the damage to that leaf's own epoch. The fix is small: add the leaf index to leanVM's claim.
2. **The statement is ordered and may repeat, a real proof is a set.** The reference concatenates signatures in statement order, and two attestations in a block may cover the same `(pubkey, message)`. leanVM's claims are strictly sorted and deduplicated. The mapping is sound (prove the sorted union) but the spec should say that order and multiplicity carry no meaning.
3. **`MAX_STARK_PROOF_SIZE` and the claim count are unrelated to the prover.** leanVM caps a merge at 16 children, and proving fails once a node holds more claims than one proof can. A block holds up to `MAX_ATTESTATIONS_PQ = 16` attestations, each spanning many committees, so a mainnet block's proof can need more claims than fit, and merging its aggregates is a tree of recursive proofs. The 1 MiB size cap is loose by comparison: proofs measured here are 160 to 205 KiB.
4. **An empty proof for no attestations is implicit.** The reference accepts empty bytes when there are no statements. A real prover has no proof of nothing, so the spec should state that a block without attestations carries an empty `proof`.
5. **The leaf layout splits a validator's leaves over two bottom trees.** Attestations use leaves from `2^15` and per-slot messages use leaves from `2^15 + 2^29 + 2^30`, after those reserved for builder bids, so the two are always in different bottom trees of a leanXMSS key (two layers of `2^16`). A signer must keep both built: leanVM keeps the four a key used last, and building one takes 5 to 6 s on one thread. The per-slot leaves start halfway into a bottom tree, so the first per-slot tree lasts 4,096 slots and each later one 8,192: the boundaries are slots 4096, 12288, 20480. A validator client has to build the next one ahead of the boundary or miss duties while it does.
6. **A VRF tree costs far more than the key it accompanies.** Depth 31 means `2^32` Keccak-256 calls per validator before it can register: 98 s on 32 threads with a scalar Keccak, against 5 s on one thread for the leanXMSS key. With SHA-256, which the spec used until `2f43bc0` and for which this client has a vectorized hasher, it was 14.5 s. It cannot be built lazily, since the root commits to every leaf. An operator with 1,000 validators needs about 27 hours of this machine. The slot index also wraps at `2^31`, since `is_valid_vrf_proof` reads only its low bits.
7. **`IndexedAttestation` reuses a removed field's index.** `Attestation` leaves a gap where `signature` was (`active_fields(width=4, gaps=(2,))`), while `IndexedAttestation` puts the new `proof` at the index `signature` had (`width=3`, no gap). Probably unintended.
8. **Builder exit requests ignore the public key's prefix.** Withdrawal and consolidation requests return early on a legacy (BLS) public key. `process_builder_exit_request` slices `pubkey[16:]` without checking the prefix, so any 16 bytes in front of a builder's key match it. The branch tests this (`builder_exit_request_ignores_pubkey_prefix`), so it is deliberate, and harmless since `source_address` authorizes the request, but it is inconsistent with the other requests.
9. **Linear scans in the hot path.** `get_validator_preregistration_index` scans up to `PREREGISTRATIONS_LIMIT` (524,288) records for every deposit request, of which a payload holds up to 8,192, and `get_builder_preregistration_index` does the same for every builder deposit. `is_pending_validator` scans every pending deposit for every validator preregistration request, and `process_voluntary_exit_request` looks its public key up in the whole registry. A client needs indexes the spec's state does not provide.
10. **The fast confirmation tests do not cover PQ.** At `a4d16c5` `make test fork=pq preset=minimal` ended with 39 failures, all in `phase0/fast_confirmation/`. `2f43bc0` skips the tests that assume a one-slot inclusion delay, and the suite passes. Fast confirmation under a two-slot delay is untested rather than shown to work.
11. **No real-signature vectors.** The generated vectors run with XMSS switched off: stub signatures, every proof accepted. They exercise the state logic and nothing of the cryptography, and there are no SSZ static vectors for the new containers. Lodestar has no such switch, so it runs them with signature checks skipped, as a caller that verified them beforehand would. Five vectors cannot run that way: they store a preregistration, whose signature block processing must always check because its validity decides the post-state.
12. **The state names the aggregators, and the beacon API cannot say who they are.** Each beacon committee has an aggregation committee of `AGGREGATORS_PER_COMMITTEE` (4) validators, sampled by effective balance and kept in `aggregation_committee_window` for the previous, current and next epochs. A validator client holds no state, and attester duties do not say whether a validator aggregates. Here attester duties carry `is_aggregator`, as they do in Lighthouse and Prysm. The count is fixed where it was an expectation: a committee whose four aggregators are offline or late has no aggregate, and its attestations reach a block only if the proposer saw the single ones on their subnet and proves them itself.
13. **There is no genesis for a PQ chain.** `upgrade_to_pq` and the test helper are the only ways to a PQ state. A network that starts at PQ needs a specified genesis: validators with leanXMSS keys and VRF roots, the previous fork version, and the genesis bid.
14. **The beacon API has no PQ forms.** Its public key fields are 48 bytes, its validator has no `vrf_root`, and `randao_reveal` is a 96-byte signature. Here duties and identities name a PQ validator by its 32-byte key in JSON, and the validators endpoints return the PQ validator itself, with its 32-byte key and `vrf_root`, and take the key as an id, as Lighthouse and Prysm do. The 48-byte form requests use (16 zero bytes, then the key) is read too, and is what the SSZ forms of these responses still hold. The API carries the 1,024-byte VRF proof where the RANDAO reveal and the selection proof went. Proposer preferences and payload attestation messages change size with their signature and need a version to decode. The forms are each client's own: on pq-devnet-0 Lodestar's validator client, pointed at other clients' beacon nodes, could not parse the aggregates they returned (`JSON expected key aggregation_bits is undefined`).
15. **The engine API has no encoding for the new requests.** The spec gives `VALIDATOR_PREREGISTRATION_REQUEST_TYPE`, `BUILDER_PREREGISTRATION_REQUEST_TYPE` and `VOLUNTARY_EXIT_REQUEST_TYPE`, and the requests list of `engine_newPayload` and `engine_getPayload` is the natural place. Here they are request types `0x07` to `0x09` after the builder exit requests.
16. **A proposer proves before it proposes.** The block's proof covers every attestation in it, so the proposer merges the proofs of its picks, or proves raw signatures no aggregate covered, before its own deadline. `MIN_ATTESTATION_INCLUSION_DELAY_PQ` (2 slots) gives it a slot for that, at the cost of every attestation landing a slot later. Whether one slot is enough at mainnet committee sizes depends on the prover: see the measurements. The spec says nothing of when to merge or of what a proposer does when the merge is late. Here, as in Lighthouse and Prysm, a node that proposes at slot `N` starts merging two thirds into slot `N - 2`, when that slot's aggregates are out, merges again when the pool has more attesters to add and the last merge's duration says another fits, and at the slot proposes what it has. Without a merged proof it merges until three quarters of the attestation deadline, then proposes without attestations.
17. **System contracts verify leanXMSS signatures, and nothing says how.** Preregistrations and voluntary exits reach the beacon chain as execution requests without a signature, because "the system contract verifies the signature". That is leanXMSS verification in the EVM, in contract code or as a precompile. Neither the contracts, the message they verify (domain, signing root) nor how they enforce a reserved leaf is specified. A consensus client can no longer check these requests at all, so a bug in a contract is a consensus bug no client catches. The mock execution engine here emits none of them: only the spec vectors exercise these paths.
18. **A voluntary exit needs an execution transaction.** A validator can no longer exit by gossip: somebody pays gas on the execution layer. The `voluntary_exit` topic, the operation pool and `POST /eth/v1/beacon/pool/voluntary_exits` have no PQ form, and this client refuses the endpoint from PQ on. Nothing replaces them for a validator whose operator has only a beacon node.
19. **Leaves the signer picks need an allocator that outlives the key's host.** A preregistration and an exit are signed at "any reserved leaf", and a bid at any of the `2^30` bid leaves, each used at most once. The record of used leaves is one more thing that must survive restarts and move with the key, beside what each attestation and slot leaf signed. Nothing here signs at these leaves yet. A verifier reads a bid's leaf from the signature with `GetLeafIndex`, which a leanXMSS signature carries in its first 4 bytes.
20. **One aggregate per committee is a BLS limit the spec kept.** `compute_on_chain_aggregate` takes one network aggregate per committee and `MergeProofs` concatenates statement lists, so two aggregates of one committee that overlap cannot become the one statement `process_stark` checks, and their attesters cannot all be included. A recursive proof has no such limit: leanVM merges overlapping children and publishes the union of their claims. The `stark` interface should define a merge as that union, and the validator guide should let a proposer combine a committee's aggregates and the single attestations none of them covers.
21. **A proof is tied to the prover's build, and nothing names it.** A leanVM proof binds the bytecode of the aggregation guest, so a change to the guest or to its compiler changes which proofs verify. Proofs made at leanVM `283686575` do not verify at `ed054a05f` or later and cannot be merged there, though signatures are byte for byte the same. Every client on a network must run the same guest, so the spec has to pin it, and changing it is a fork.
22. **A reorg onto a block without its payload rolls the execution chain back, and execution clients limit how far.** When the new head's payload was never revealed, the execution head a client asks for is that block's parent payload, which is already on the execution client's chain and below its head. geth refuses such a rollback beyond 32 blocks by default (`--engine.maxreorgdepth`, error `-38006`), and the execution API leaves the depth to each client. On pq-devnet-0 a 98-slot reorg onto a block without its payload needed a rollback of 54 blocks, every geth refused it, and no node could build a block until the limit was lifted. This is Gloas behaviour, not PQ, and ethpandaops found it. A limit that does not reach back to the finalized block can halt a chain, as it did here.

## Implementation difficulties

1. **The validator type changes.** Every fork before PQ shares one `Validator` container. PQ's has a 32-byte key and a `vrf_root`, so code that reads validators from a fork-neutral state had to become generic, and the fork-neutral list wrapper refuses element access for PQ.
2. **Public key lookup.** The cache maps 48-byte BLS keys to validator indices and holds each key's decompressed point. For PQ it holds the key as deposits name it, 16 zero bytes then the leanXMSS key, with an unused point.
3. **Committee count and inclusion delay were constants.** `MAX_COMMITTEES_PER_SLOT_PQ` and `MIN_ATTESTATION_INCLUSION_DELAY_PQ` replace values that shuffling, attestation validation, the participation flags and the byte readers of gossip messages took as global. Shuffling in particular had no notion of a fork: it now takes the committee cap from the state's. The timely head flag needs the slot of the block an attestation voted for, which with a delay of two slots may be the grandparent, found by walking block roots back (`get_latest_block_slot`).
4. **leanVM allocates through its own global allocator.** The Rust library is linked into every binary that imports the state transition, and its allocator symbols come from the `leanvm` Zig module, which must therefore be analyzed in each of them.
5. **One aggregation at a time.** leanVM runs one `aggregate` call at a time in a process and queues the rest. A node that aggregates for several committees and then merges as proposer queues behind itself.
6. **Fixed offsets into serialized messages.** Gossip and the database read a slot or a root out of serialized bytes at offsets that assume a 96-byte signature: signed blocks, envelopes, bids, the envelope archive. Each now reads the message's offset, which sits past the signature and so says how long it is.
7. **Types that were one per fork family.** Envelopes, proposer preferences and payload attestation messages had one SSZ type from Gloas on. PQ's differ by the signature, and the envelope by its execution requests too, so every use needs the slot or the fork: gossip topics, req/resp, the database, the API.
8. **Leaf reuse outlives a restart.** What each leaf signed is kept in the validator database beside slashing protection. Attestation and block leaves are already covered by slashing protection, which refuses a second vote for a target epoch and a second block for a slot. Aggregates, payload attestations, envelopes and proposer preferences are not.
9. **Payload attestations have no pool.** A PQ block carries none, so they reach fork choice from gossip and the BLS aggregation pool is skipped.
10. **Signing is single-threaded and slow.** leanVM generates a key, builds a bottom tree and grinds a signature's randomizer on the calling thread. A signature takes 0.3 s on average and varies widely, which is a visible share of a slot's first third, and a validator client with many keys signs as many at once as it has threads. Key generation at 5 s a key made `lodestar dev` start its genesis late until keys were generated before the genesis time was chosen. One slow signature is enough to fork the chain: on the devnet below a payload envelope's signature took 2.9 s, the envelope missed the payload attestation deadline, the next proposer built on the block without its payload and the one after on the block with it, and two blocks were orphaned before the chain settled.
11. **Tree builds for many keys starve the rest of the validator client.** leanVM work runs on libuv's pool, four threads by default, which signing and DNS lookups share. The client built the next bottom tree for every key at once, one epoch before the boundary. On pq-devnet-0, with 625 keys a client, that filled the pool at slot 4064: both validator clients stopped signing for 21 minutes and logged connect timeouts to their beacon nodes, and one published the blocks of slots 4070 and 4075 19 minutes late. Block 4075 carried the attestations that justified epoch 126 on its branch only, so every client reorged 98 slots onto it. The client now builds the trees for 2,048 slots ahead, one key at a time, each epoch. The builds still share the pool with signing.
12. **Range sync could not cross an epoch without blocks.** A by-range response with no blocks was rejected, although it is the right answer for an epoch in which every slot was missed, and the look-ahead window counted empty batches, which never advance it. pq-devnet-0 has 37 such epochs in a row (128 to 164), and both Lodestar nodes stopped at slot 4075 while every other client synced past. This is not PQ: `unstable` has the same code. See the differences from `unstable` below.

## Measurements

| Operation                                 | Time    |
| ----------------------------------------- | ------- |
| leanXMSS key generation                   | 5.3 s   |
| First signature in a bottom tree          | 5.9 s   |
| Later signatures in that tree, mean of 64 | 0.29 s  |
| Signature verification                    | 0.07 ms |
| VRF tree, depth 31                        | 98 s    |
| VRF proof after a subtree rebuild         | 47 ms   |

leanXMSS runs on one thread. Signing grinds a randomizer, so single signatures vary widely around the mean.

Aggregation at `log_inv_rate = 2`:

| Signatures | Prove  | Proof size    | Verify |
| ---------- | ------ | ------------- | ------ |
| 16         | 0.16 s | 161,744 bytes | 22 ms  |
| 64         | 0.27 s | 174,860 bytes | 22 ms  |
| 256        | 0.61 s | 190,800 bytes | 23 ms  |
| 1024       | 2.2 s  | 204,892 bytes | 23 ms  |

Merging two aggregates into one takes 0.4 to 0.6 s whatever their size, more than proving 64 signatures from scratch. Through the Node addon 1,400 signatures take 2.9 s. leanVM's own CLI proves them in 2.6 s on this machine, and a 16-to-1 merge of such aggregates in 2.9 s.

Memory, before leanVM kept one level of each tree: about 2 MiB per loaded key, and 2 MiB more once it has signed. A key now keeps 4 KiB a tree. A VRF tree keeps 6 MiB, of which 2 MiB is needed between proofs.

On the devnet below (8 validators, one per committee, minimal preset, node and validator client on this machine) a block was published a median of 0.76 s into its slot and at most 1.5 s, over 47 blocks. That includes proving the block's attestations. It finalized epoch 3 in 47 slots, with two blocks orphaned by the slow signature described above.

A validator client keeps each key's trees in its cache directory (the top tree and two bottom trees) and loads them at the next start. For 32 keys, on libuv's four threads, measured when a tree kept `2^10` nodes: 44 s to derive the keys and 89 s to build their bottom trees without the files, 2.2 s and 0.01 s with them. What is left is the VRF trees' first `2^20` leaves, about a second of one core a key. Only a proposal needs a VRF tree, so the client starts without them and builds them behind its start, one at a time, and at once for a validator that proposes before its turn, as Lighthouse and Prysm build theirs in the background. A tree whose root is not the one the state holds for the validator opens no slot. A first start takes the trees from `--xmssCacheUrl`, a file of them, 14,696 bytes a validator, in the order of the validator registry. The trees are checked against the public key, which a client with only a keystore does not have before it builds the key. What it has for nothing is the key's public parameter, the last 16 bytes of the public key, so it lists the registry's public keys from its beacon node and finds its own by that: the public key it then trusts is the one in the state, and the validator's index is its record's. Prysm does the same. Lighthouse carries the devnet's 10,000 public keys in its binary, as Lodestar did at first. The file's order is the registry's only while the registry is the genesis one.

On pq-devnet-0 (10,000 validators, mainnet preset, 625 keys a validator client, the network's own hosts) the client built the bottom trees for the boundary at slot 12288 ahead, one key at a time while it kept signing: 8,936 s on one host and 10,601 s on the other, 14 to 17 s a key against 5 to 6 s for a tree built alone. For the boundary at slot 20480 the builds took 8,288 s and 13,360 s, the second on a host that had 3 to 3.5 of its 8 CPUs taken by the hypervisor, and ended 4.6 and 3.2 hours ahead. Both clients then crossed the boundary with no skipped slot, no failed signature and no lost proposal, where at slot 4096 the trees, built for every key at once one epoch ahead, had stopped their signing for about 21 minutes. The builds cost duties while they ran: on the first host the attestations that arrived by their deadline fell from about 75% to 40%, and on the second, the one short of CPU, 36 of 83 proposals were orphaned. The VRF trees of 625 keys took 835 s to 3,133 s after a restart. A node without validators, on an 11-core Apple laptop with a mock execution engine, synced from genesis to the head at slot 11,550 in 21 minutes, 10 to 30 slots a second.

With Teku at `dcbe4f7`, the same spec commit with leanVM bindings 0.17.0, under kurtosis on an 11-core Apple laptop: one node of each client, 64 validators each, mainnet preset. In 135 slots no slot was missed, Lodestar proposed 59 blocks and Teku 76, both nodes kept one head, and epoch 2 was finalized by slot 135. Each client verified the other's aggregates and block proofs, so a proof of bindings 0.17.0 verifies at 0.18.0 and the reverse. The validator client asked for a committee's aggregate 7.2, 7.8, 8.4 or 9.0 s into the slot, by the position of its first aggregator in the aggregation committee, and the beacon node answered in a median of 4 ms and at most 16 ms, as the proof was made at the cutoff. First in the order it published 61 times of 61. Behind another aggregator it published once and had nothing to publish 65 times, as an aggregate it had received already included its attesters.

## Not implemented

- EIP-8483 and `upgrade_to_pq`: the chain starts at PQ. That leaves out the rules for validators and builders that did not register, `UNREGISTERED_VALIDATOR_WITHDRAWABILITY_DELAY` among them.
- What the branch took from its merges of `master` into Gloas and Heze: the per-builder bid limit on gossip, the added envelope gossip checks, the fast confirmation changes.
- Signing at reserved and builder bid leaves: no preregistration, exit or external bid is produced.
- The `pq` commits after `4595f0fc`: VRF leaves that commit to a secret (`b5d422b2`), `X_MAX_COMMITTEE_COUNT_PER_SLOT` (`af898d07`), and Keccak-256 for the keys and VRF roots of legacy requests (`4c296784`). pq-devnet-1's notes ask for a spec at or after `4595f0fc`, and Teku's branch is at `4c296784`, whose VRF roots are not this branch's.

## Differences from unstable

- Range sync accepts a by-range response with no blocks, skips sidecar validation for a range without blocks, and leaves batches that await validation out of the look-ahead window (`f170cd60a5`). It is a stopgap for pq-devnet-0, to be replaced by the fix for ChainSafe/lodestar#10772. A local node with it crossed the 37 empty epochs in 16 s. One without it stayed at slot 4075.

## Known issues

Open on this branch after the first two days of pq-devnet-0.

1. **Tree builds share libuv's pool with signing.** The validator client builds each key's next bottom tree ahead, one key at a time, but on the pool that signs and resolves names. A build that takes 5 to 6 s alone took 14 to 17 s there, and signatures wait behind it. The builds start 2,048 slots, or 6.8 hours, before a boundary, so at that rate a client with more than about 1,400 keys does not finish in time. The builds need threads of their own.
2. **Attestations are published late.** The client signed a slot's attestations as many at once as the pool has threads and sent them in one request when the last was signed. Since `4a70a4bb1f` it publishes each attestation when its signature is done, with one request in flight at a time, as Lighthouse, Prysm and Teku do. Signing is still limited by the pool. Measured on pq-devnet-0 as the first arrival of each attestation at the Lighthouse nodes, in two periods when the hosts were not short of CPU (issue 3): before the change, the median Lodestar attestation arrived 3.0 to 3.1 s into the slot and 47 to 48% arrived by the 3 s deadline, against 1.8 s and 79% for the other clients. After it, 1.7 to 2.0 s and 83 to 89%, against 1.6 s and 93%. What is left is the tail: the slowest tenth arrives after 3.1 to 3.4 s, against 2.8 s for the others.
3. **The client has no margin when its host is short of CPU.** Both Lodestar hosts on pq-devnet-0 have 8 virtual CPUs, and for hours at a time 2 to 3.5 of them are reported as steal, which is time the hypervisor gave to another guest. Of the 18 hosts only these two and `teku-geth-1` show it, and why is not known. On 25 November, with steal under 0.6 CPUs (12:30 to 14:15 UTC), blocks reached the network a median of 0.9 s into the slot and none of 69 proposals was orphaned. With steal above 2 CPUs (15:30 to 17:30 UTC), blocks arrived at 2.7 to 3.1 s, 19 of 82 proposals were orphaned and 44 of the 62 that stayed carried no attestations, because the block's proof was not merged by its deadline ("Proposing without attestations: their proofs did not merge in time"). In the validator client the request for an aggregate timed out after 12 s, the slot's work overran ("Skipped slot due to task taking more than one slot"), and payload attestations went out a slot late and were refused. `teku-geth-1`, with the same steal, lost no proposal. `lodestar-geth-2` showed the same on `f170cd60a5` from 14:30 UTC, before issue 2's change reached it, and both hosts recovered on `4a70a4bb1f` without a restart when the steal fell below about 1.2 CPUs in the evening, so the change is not the cause. Attestations suffer the same way: with steal above 2 CPUs the median arrived 3.8 to 5.3 s into the slot and a quarter of `lodestar-geth-2`'s were not made at all.
4. **The range sync stopgap trusts an empty answer more than it should.** Found by reading, not reproduced, and none of it applies to pq-devnet-0 while its peers are honest. Only the first batch of a sync chain can ask for a missing parent payload by root, and it needs a block to do so: if that batch is empty, the first block after the gap can fail with `PARENT_PAYLOAD_UNKNOWN`. A sync chain is done when it reaches the target's slot, whether or not it has the target's root, so an empty answer for the last batch ends it early. And when a block does not link to the empty batch before it, its own batch is charged a processing attempt before the earlier batches are downloaded again, so a peer that hides blocks can use up the attempts of the peer that serves them.
5. **Tree files of removed keys are never deleted.** The validator client keeps two files per key in `xmss-trees`: the key's leanXMSS trees, up to 46 KiB now that a key keeps 8 bottom trees, and the subtree roots of its VRF tree, 545 bytes. Old trees leave a key's file as the key moves on, so a file does not grow. But removing a key, through the keymanager or by deleting its keystore, leaves both files, and a stop in the middle of a write can leave a `.tmp` file. They hold no secret and are not loaded for any other key, so the cost is disk space only. Deleting a key should delete its files.
6. **An attester duty always has an aggregator position.** The beacon API draft (ethereum/beacon-APIs#684) gives `aggregator_position` only to an aggregator and `is_aggregator` only from PQ. This branch's duty has both always, zero and false where they do not apply, and its validator client refuses a duty without them, so it cannot take its duties from another client's beacon node.

Closed: from 12:03 UTC on 24 November to 06:49 UTC on 25 November both validator clients on pq-devnet-0 used `https://beacon.pq-devnet-0.ethpandaops.io`, which is Dugtrio, a load balancer in front of the beacon nodes of all eight clients, instead of their own beacon nodes. In that time none of Lodestar's proposals had a payload, because the envelope is held by the node that built the block and the request for it went to another (`getExecutionPayloadEnvelope failed with status 404`), and aggregates from other clients' nodes did not parse (`aggregation_bits is undefined`, see spec deficiency 14). It was a setting of the devnet and not a fault of the client. Since ethpandaops pointed them back, all 375 Lodestar proposals up to slot 15316 that stayed in the chain have their payload, and both errors are gone.

## Running a devnet

```sh
pnpm build
./lodestar dev --genesisValidators 8 --startValidators 0..7 --reset \
  --params.GLOAS_FORK_EPOCH 0 --params.PQ_FORK_EPOCH 0
```

`dev` uses the minimal preset and a mock execution engine. For more nodes give each the same `--genesisValidators` and `--genesisTime`, its own `--startValidators` range, `--dataDir` and ports, and the first node's ENR as `--bootnodes` with `--network.connectToDiscv5Bootnodes`, as `docs/pages/contribution/advanced-topics/setting-up-a-testnet.md` describes. With `PQ_FORK_EPOCH` 0 it builds a PQ genesis state (`initDevStatePq`) whose validators are the interop leanXMSS keys the validator client derives from each index. Interop VRF trees hold secrets for the first 2^20 slots only. Every signature and every proof is real: there is no switch to turn verification off.

To follow pq-devnet-0 with a local node, take `config.yaml` and `genesis.ssz` from `https://config.pq-devnet-0.ethpandaops.io/cl/` and the consensus ENRs of its nodes from `https://config.pq-devnet-0.ethpandaops.io/api/v1/nodes/inventory`:

```sh
./lodestar beacon --paramsFile config.yaml --genesisStateFile genesis.ssz \
  --bootnodes <enr>,<enr> --network.connectToDiscv5Bootnodes \
  --execution.engineMock --dataDir <dir>
```

The mock execution engine does not execute payloads, so this exercises sync and consensus only.

## Recording timings

`--pqTimingOutput <dir>` on a beacon node records when PQ attestations and aggregates arrive, what gossip validation made of each, and every proof it makes: the committee proofs of its aggregators, the merges ahead of its proposals, the merge in the slot when there was none, and what the proposer had when its slot came. Each run is a directory with `run.json` and chunks of zstd compressed JSON lines, in the format of Lighthouse's `scripts/pq-measurement`, which Prysm writes too, so Lighthouse's `plot.py` renders a run of any of the three clients.

`--pqMeasurement` makes a node without validators an observer: it subscribes to every attestation subnet and, every third slot, does on what the network sent the proving of an aggregator (one committee's single attestations, proven halfway between the attestation and the aggregate deadlines), of a proposer (the merge for a block two slots on, redone while it gains, until that slot), or both. What it proves stays out of the pool and off the network. It records as `--pqTimingOutput` does, in `pq-timing` of the data directory unless told where. A node with validators skips every experiment: the prover is theirs first.

Where this record differs from Lighthouse's:

- A receipt is stamped when gossipsub delivers the message, to the millisecond, and written with its validation outcome, so a message that does not decode has no receipt.
- leanVM runs in the process and queues proofs itself, so a proof's duration holds whatever it waited behind another, and there is no queue wait of its own.
- A committee of this node's own aggregators is proven at the cutoff of the first of them in the aggregation committee, for the validator client to fetch when that aggregator's aggregate is due. An aggregator the validator client names in its slot or not at all is proven for when it asks, and its proof is late by its own duration. The observer proves at the first aggregator's cutoff.
- The observer does not verify the proofs it merges, only the committee proofs.
- `lodestar dev` with validators stops through the validator client, which exits the process before the beacon node closes: the run's last chunk, up to five minutes, is then not listed in `run.json`. A beacon node on its own closes its run.
